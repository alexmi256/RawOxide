# RawHide (Rust)

Rust port of the Python [RawHide](../RawHide) DNG steganography toolkit. The
goal is a self-contained native CLI: one binary, no Python/NumPy/Pillow
dependency, lower memory use at multi-gigabyte scale, and the same on-disk
format so either implementation can decode the other's files.

> **Status:** decode works end to end against Python-generated DNGs, and the
> writer produces tiled `LinearRaw`/`CFA` DNGs at 8/10/12/14/16-bit with a
> baseline JPEG preview, multiple raw frames (1-8), split chunk sets with EXIF
> markers, embedded payload, auto-sizing/auto-planes and seeded EXIF/DNG
> metadata. All 307 Python camera profiles are embedded, and `--camera-profile`
> drives calibration, metadata pools and tag values. Python, `tifffile`,
> `exiv2`, `tiffdump` and `rawpy` accept the output. GPS sampling, thumbnails,
> opcodes/digests, Deflate/BigTIFF output and streaming writes are planned in
> [docs/port-plan.md](docs/port-plan.md).

## Quick start

```bash
cargo run -p rawhide-cli -- capacity --width 2048 --height 1536
# samples: 9437184
# capacity (1 LSB plane(s)): 1,152.0 KB

cargo run -p rawhide-cli -- decode \
  -i fixtures/dng/linear_256x192_16bit_1plane.dng \
  -o /tmp/recovered.bin

# writer: preset auto-config (2048x1536 for a tiny payload) + JPEG preview
cargo run -p rawhide-cli -- encode \
  -i fixtures/payloads/payload_3000.bin \
  -o /tmp/spike.dng

# multi-frame raw + split chunk set (2 chunks of ~3000 bytes)
cargo run -p rawhide-cli -- encode \
  -i fixtures/payloads/payload_5000.bin \
  -o /tmp/vol.dng --raw-frames 3 --split-file 3000

# camera profile, minimal geometry, pinned capture time
cargo run -p rawhide-cli -- encode \
  -i fixtures/payloads/payload_3000.bin -o /tmp/canon.dng \
  --camera-profile canon_eos_80d --auto-size \
  --image-time "2021:06:05 14:30:09"

cargo test --workspace
```

## Layout

| path | purpose |
|---|---|
| `crates/rawhide-core/` | library: framing, LSB codec, TIFF/DNG, metadata (in progress) |
| `crates/rawhide-cli/` | `rawhide` binary (clap) |
| `fixtures/` | small committed DNGs and golden vectors generated by the Python oracle |
| `assets/profiles/` | embedded camera registry copied from the Python profiles |
| `scripts/` | fixture generation and Python-oracle helpers |
| `docs/` | port plan, architecture, testing and ADRs |
| `../.github/workflows/rust-ci.yml` | CI: fmt, clippy, tests, coverage, deny, audit, docs |

| task | command |
|---|---|
| format | `just fmt` / `cargo fmt --all` |
| format check | `just fmt-check` |
| lint | `just lint` (`clippy -D warnings`) |
| type check | `just check` (`cargo check --all-targets`) |
| tests | `just test` (`cargo nextest`) |
| doc tests | `just test-doc` |
| coverage | `just coverage` (`cargo llvm-cov nextest`) |
| licenses/advisories | `just deny`, `just audit` |
| docs | `just doc` (`RUSTDOCFLAGS=-D warnings`) |
| benchmarks | `just bench` |
| mutation tests | `just mutants` (optional) |
| full local CI | `just ci` |

Required tools: Rust 1.88+ (the workspace uses edition 2024). `just` is
optional but recommended. The CI-only tools are user-level installs:

```bash
cargo install --locked cargo-nextest cargo-llvm-cov cargo-deny cargo-audit cargo-insta
```

The repo is set up for `rustup`: `rust-toolchain.toml` selects stable with
`rustfmt`, `clippy` and `llvm-tools-preview`, so `just coverage` needs no extra
environment. If the LLVM tools are absent, the coverage recipe falls back to the
system `llvm-cov`/`llvm-profdata`:

```bash
LLVM_COV=/usr/bin/llvm-cov LLVM_PROFDATA=/usr/bin/llvm-profdata just coverage
```

Optional local acceleration (machine-specific; not committed to the repo):

```bash
RUSTC_WRAPPER=sccache cargo check --workspace --all-targets --all-features
RUSTFLAGS='-C link-arg=-fuse-ld=mold' cargo build -p rawhide-cli
/usr/bin/time -v cargo run -p rawhide-cli -- capacity --width 2048 --height 1536
```

## Compatibility policy

The port is **outcome-compatible**, not byte-identical or structurally identical,
with the Python tool: files written by either implementation decode in the other,
the same payload/key/split semantics hold, and real DNG readers accept the
output. Internal choices are free — IFD/tag ordering, dummy-tag workarounds,
strip vs tile layout, EXIF/GPS construction, JPEG/Lanczos implementation, RNG
draw order, profile storage and metadata pool order may differ. See
[docs/adr/0001-format-compatibility.md](docs/adr/0001-format-compatibility.md).
